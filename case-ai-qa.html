Testing what nobody has tested before

The product started shipping AI-assisted features, and every method in the existing test suite assumed the same input produces the same output. I built the harness, the scenario corpus and the pass criteria that made those features releasable on a schedule.

Context

DocuPet's regression suite was in good shape — a Playwright suite in CI, results on every pull request, a defect process that worked. Then AI-assisted features entered the roadmap and the suite had no answer for them. An assertion that expects an exact string fails on a rephrasing that is entirely correct, and passes on an answer that is fluent and wrong.

The default response on most teams is one of two failures: skip automated coverage entirely and rely on someone reading outputs before release, or write brittle string assertions that get muted within two sprints. Neither survives contact with a release cadence.

The problem

Stated as a cost: without a defined pass criterion, no one could say whether a prompt change had made the feature better or worse. Release decisions came down to whoever had looked at the output most recently. That is unreviewable, unrepeatable, and it does not scale past one feature.

What I built

Three pieces, each solving one part of the problem.

A fixed harness. Model version, temperature, system prompt and retrieved context all pinned per test run. If output changed, exactly one thing had changed — otherwise the result is noise and the team learns to ignore it.

An edge-case scenario library. A maintained corpus of inputs grouped by the failure they provoke: ambiguity, adversarial phrasing, empty and overlong input, out-of-scope requests, and domain-specific cases particular to the product. Every production issue added a case. The corpus is the institutional memory of everything that has gone wrong.

Property-based pass criteria. Instead of asserting on text, assert on properties the output must hold regardless of phrasing — schema validity, no entities that weren't in the input, refusal behaviour on out-of-scope requests, length and tone within range. Then a threshold across the corpus, agreed with the product owner in advance, that gates the merge.

Assertion pattern — sanitized

scenario:  user submits an ambiguous request
fixture:   locked model version, temperature, system prompt
input:     corpus/ambiguous/*.json          (48 cases)

assert response.schema            valid
assert response.entities ⊆ input.entities
assert response.contains_refusal  when input.out_of_scope
assert response.length            within 1..3 sentences
assert response.tone              in [neutral, helpful]

gate:      ≥ 46 / 48 pass  →  promote
           < 46 / 48 pass  →  block merge, diff vs baseline

Result

  • Prompt changes became reviewable. A pull request that alters a prompt now produces a diff against a baseline instead of an opinion.
  • The release conversation changed from "does this look right to you" to "it passes at the agreed threshold, here are the two cases that regressed".
  • The scenario corpus became a shared artifact — product and engineering contribute cases, not just QA.
